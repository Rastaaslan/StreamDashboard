# F08 — Libération explicite après état Twitch terminal (sources de développement)

## Périmètre
Régie unique FIXE uniquement. Aucune commande Twitch publique, aucun arrêt OBS ni installation utilisateur. Ce protocole ne verrouille, résout ou annule PAS une prédiction Twitch : il ne fait que retirer la réservation locale d'une prédiction déjà identifiée et déclarée RESOLVED/CANCELED par Twitch. L'absence (not_found), une erreur OAuth, l'absence d'identifiant, le journal v1 et toute issue incertaine ne suffisent jamais. Ce parcours n'est PAS encore intégré à l'interface Android.

## Contrat HTTP et sécurité
- GET /api/v1/twitch/advanced/prediction/reconcile reste strictement en lecture seule : l'observation actuelle ne libère jamais le verrou.
- POST /api/v1/twitch/advanced/prediction/reconcile/preview avec corps JSON {} : appairage de gestion avec droits chat+cloud, OBS FIXE réellement observé en live, époque stable, propriétaire Twitch/OAuth valide, identifiant durable exact lu en SQLite. L'API demande à Twitch par GET exact ID et ne propose de token de consentement que si le statut est resolved ou canceled. Token UUID aléatoire en mémoire, lié à acteur, propriétaire, ID et époque OBS, durée <=45 s. Aucun effacement de base, aucun POST Twitch.
- POST /api/v1/twitch/advanced/prediction/reconcile/confirm : JSON strict { "confirmationId": "<uuid retourné>", "confirmed": true }. Le token est consommé avant le premier await. Refus si acteur, époque FIXE, propriétaire ou ID ont changé, si token expiré, si autre libération en cours. Nouveau GET Twitch exact ID avec contrôle OAuth et statut terminal, puis nouvelle validation acteur/OBS/propriétaire et ID du journal, et enfin transaction SQLite DELETE WHERE broadcaster_id=? AND prediction_id=? (CAS exact). La barrière en mémoire n'est ouverte qu'après confirmation de cette transaction. Aucun retry automatique d'écriture fournisseur et aucune opération sur OBS.
- Réponses private, no-store ; seuls POST sont acceptés pour les deux gestes. Pairing limité, erreur, transition stop/restart, résultat actif/verrouillé/non trouvé, identité ou jeton changé : aucune suppression.
- En cas d'erreur ou commit SQLite incertain, l'API répond sans prétendre avoir libéré ; l'opérateur doit réinspecter l'état réel du journal. L'atomicité Twitch/SQLite/OBS et la durabilité électrique ne sont PAS démontrées.

## Preuves et limites
Tests via HTTP Express local réel avec Twitch simulé, node:sqlite sur fichier temporaire NTFS du FIXE ; incluent anti-duplication, révocation, état terminal devenu actif entre les deux gestes, autorisation appairage et redémarrage logique. Pas de vrai compte OAuth, aucune prédiction publiée ou résolue, aucune panne électrique réelle, ni dossier de données de production, ni Android/laptop physique. Il reste à créer le parcours d'interface opérateur, à évaluer un journal d'audit durable des décisions et à qualifier les migrations, le rollback, la signature et l'exécution réelle avant G3–G5.
